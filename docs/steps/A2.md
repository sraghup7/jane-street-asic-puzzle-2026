# Step A2 — The connectivity rule set

**Stage:** `python -m tools.puzzle via-pairs` · **Gate:** `tools/checks/check_stepA2.py` → **27/27 PASS**
**Artifact:** `recon/derived/via_pairs.json` · **Input:** `recon/derived/layers.json` (A1)
**Differentiator:** D1 — the chip's own vias define the stack

A1 said *which* layers are cuts and conductors. A2 answers the operational question: **which pair
of conductors does each cut actually bridge?** That rule set is what B2/B3 will use to trace nets.

---

## 1. Method — proved by shared area, not by layer names

For every via master, for every cut layer in it, for every conductor in it, the code computes the
**exact polygon intersection area** between each cut shape and each conductor shape
(`gdstk.boolean(..., 'and')`, bbox-rejected first). A cut is recorded as bridging a conductor only
if they share non-zero area.

That matters because the via-master names in this file are unusable, and not merely ambiguous. Two
naming families coexist and they disagree about what the same digit means:

| master | bridges |
|---|---|
| `VIA_M2M3_PR` | `69/20` ↔ `70/20` |
| `VIA_via2_3_2000_480_1_6_320_320` | `68/20` ↔ `69/20` |
| `VIA_M3M4_PR` | `70/20` ↔ `71/20` |
| `VIA_via5_6_2000_2000_1_1_1600_1600` | `71/20` ↔ `72/20` |

Both `M2M3` and `via2_3` say "2" and "3", yet they bridge pairs one layer apart. No single index
convention explains both, so any arithmetic over these names mis-assigns at least one master — and
the name `via5_6` sits on `met4`→`met5`. This is the same error class as the published work's
`via3` datatype bug (their trap T6); here the names are simply never read. The pair comes from
geometry, and the gate asserts this contradiction so nobody later "simplifies" the code by parsing
the names.

**Which cells count as via masters** is also decided structurally: a via master is a cell whose
geometry consists *only* of conductors and cuts. No cell names are consulted. This correctly
excludes the 69 standard cells (they contain `64/20`, `65/20`, `66/20` device geometry) even though
every one of them *also* contains `67/44` used as a cell-internal contact — see §4.

## 2. The via masters, with the enclosure invariant

| master | cut | bridges | instances | shared area with each metal |
|---|---|---|---|---|
| `VIA_L1M1_PR_MR` | `67/44` | `67/20` ↔ `68/20` | 2696 | 0.0289 / 0.0289 |
| `VIA_M1M2_PR` | `68/44` | `68/20` ↔ `69/20` | 3154 | 0.0225 / 0.0225 |
| `VIA_M1M2_PR_MR` | `68/44` | `68/20` ↔ `69/20` | 7 | 0.0225 / 0.0225 |
| `VIA_M2M3_PR` | `69/44` | `69/20` ↔ `70/20` | 333 | 0.0400 / 0.0400 |
| `VIA_M3M4_PR` | `70/44` | `70/20` ↔ `71/20` | 69 | 0.0400 / 0.0400 |
| `VIA_via2_3_2000_480_1_6_320_320` | `68/44` | `68/20` ↔ `69/20` | 618 | 0.1350 / 0.1350 |
| `VIA_via3_4_2000_480_1_5_400_400` | `69/44` | `69/20` ↔ `70/20` | 618 | 0.2000 / 0.2000 |
| `VIA_via4_5_2000_480_1_5_400_400` | `70/44` | `70/20` ↔ `71/20` | 618 | 0.2000 / 0.2000 |
| `VIA_via5_6_2000_2000_1_1_1600_1600` | `71/44` | `71/20` ↔ `72/20` | 108 | 0.6400 / 0.6400 |

**9 via masters, all well formed.** Total: **8221 instances** — exactly Step 1's independently
measured routed-via count.

The decisive evidence is the two shared-area columns being *equal to the cut's own area*. For
`VIA_L1M1_PR_MR` the cut is a single 0.17 µm square (area 0.0289 µm²) and it shares 0.0289 µm² with
*both* metals — the cut is entirely inside the overlap of the two conductors. That is the
**enclosure invariant** a real via must satisfy, and the gate asserts it for every cut of every
master:

```
|shared_area(cut, metal) − cut_area| ≤ 1e-6      for both metals, all 9 masters
```

If a cut only partially overlapped a metal, or reached a third layer, this would fail. It also
confirms the multi-cut vias: `via2_3` has six 0.15 µm cuts (6 × 0.0225 = 0.1350) and shares exactly
0.1350 with each metal.

## 3. The rule set and the conductor graph

| cut | bridges | from master(s) | instances |
|---|---|---|---|
| `67/44` | `67/20` ↔ `68/20` | 1 | 2696 |
| `68/44` | `68/20` ↔ `69/20` | 3 | 3779 |
| `69/44` | `69/20` ↔ `70/20` | 2 | 951 |
| `70/44` | `70/20` ↔ `71/20` | 2 | 687 |
| `71/44` | `71/20` ↔ `72/20` | 1 | 108 |

Sum = **8221**, matching the master-level accounting exactly.

The graph built from those five edges is a **single unbranched path over all six conductors**:

```
67/20 -- 68/20 -- 69/20 -- 70/20 -- 71/20 -- 72/20
```

Degrees are `[1, 1, 2, 2, 2, 2]` — two endpoints, no branches, no disconnected layer. The gate also
asserts the endpoints are the lowest and highest conductor, so the chain runs monotonically. This is
the same conclusion A1 reached from layer-set membership, now reached independently from polygon
geometry. **Two different methods, same stack.**

Two details worth recording:

- `VIA_L1M1_PR_MR` is the **only** li1↔met1 via in the file — its non-mirrored twin
  `VIA_L1M1_PR` does not exist. The gate pins this so a future reader does not "fix" the asymmetry.
- `VIA_M1M2_PR` and `VIA_M1M2_PR_MR` bridge the same pair, so the mirrored variant is genuinely
  redundant for connectivity purposes.

## 4. Finding: every standard cell uses a cut layer internally

An unplanned result that would break a naive extractor:

```
cuts ['67/44'] in 69 cells, 1618 instances
```

All **69** standard cells contain `67/44` (the li1↔met1 cut) used *inside the cell*, and the instance
count is **1618** — exactly the number of standard-cell placements. So `67/44` is simultaneously:

- a **top-level via cut** (`VIA_L1M1_PR_MR`, 2696 instances), *and*
- a **cell-internal contact** in every standard cell (1618 instances).

A rule table keyed on "which layers does this cut bridge" is fine; a rule table keyed on
"where does this cut appear" would have gone wrong immediately. The artifact records these cells
separately (`cells_using_cuts_internally`) so the distinction is visible rather than folded in.

## 5. Finding: two contact layers that no via master uses

A1 classified `66/44` and `122/16` as `contact` — cut-shaped, but with no via master referencing
them, so A2 must resolve them geometrically instead:

| layer | shapes | overlaps (counts) | reading |
|---|---|---|---|
| `66/44` | 2085 | `67/20` 2083 · `65/20` 1681 · `64/20` 1042 · `94/20` 996 · `93/44` 714 · `66/20` 403 · `95/20` 401 · `68/20` 41 · `65/44` 3 | **a shared contact layer.** It reaches li1 above in 2083 of 2085 cases, and from below reaches *either* diffusion (`65/20`) or poly (`66/20`) — 1681 + 403 ≈ 2084. One layer serving two different device terminals. |
| `122/16` | 71 | `93/44` 71 · `67/20` 70 · `68/20` 8 | Contacts li1 (and, in 8 cases, met1). Consistent with A1's finding that its geometry mirrors the `64/16` pin geometry. |

`66/44` is the trap: it is **not** a single fixed pair. Asking "what does `66/44` bridge?" has two
answers depending on the shape. Anything downstream that needs cell-internal device connectivity
would have to treat it per-shape. For our purposes it is recorded, not used — we extract at cell
granularity, and the cell's internal behaviour comes from its own type, not from tracing its
diffusions.

The remaining overlap partners (`64/20` well, `93/44`, `94/20`, `95/20`) are the layers whose
semantics A1 left unresolved; they share area with the contacts because they cover the same silicon,
not because they carry the net.

## 6. What the gate asserts

27 checks:

1. **Regenerability** — the gate re-derives the entire rule set from the GDS with a fresh
   `derive_via_pairs` call and requires a **byte-identical** document. Nothing is taken on trust.
2. **The via masters** — 9 of them; exactly one cut each; every cut connects exactly two conductors;
   every master well formed.
3. **The enclosure invariant** — shared area equals cut area for both metals, all masters; and the
   same conclusion from independent bbox containment.
4. **The rule set** — exactly the five expected cut→pair rules; every cut layer yields exactly one
   rule; the rule set covers exactly A1's `via_cut` layers.
5. **The graph** — nodes are A1's `routing` + `local_wire` layers; connected; a simple path with two
   endpoints; runs lowest to highest.
6. **Accounting** — 8221 instances from the master side, 8221 from the rule side, mirroring Step 1;
   every master instantiated; the mirror asymmetry pinned.
7. **The two findings above** — 69 internal-cut cells / 1618 instances, and both unclaimed contact
   layers with their partner sets.

## 7. Carried forward

The complete, proved connectivity stack for B2/B3, with no reference file in the loop:

```
cut  67/44 : 67/20 <-> 68/20
cut  68/44 : 68/20 <-> 69/20
cut  69/44 : 69/20 <-> 70/20
cut  70/44 : 70/20 <-> 71/20
cut  71/44 : 71/20 <-> 72/20
```

- **A3** extracts pin *names* from A1's 8 label layers; this step's `cells_using_cuts_internally`
  list tells A3 that `67/44` appearing inside a standard cell is normal, not a stray cut.
- **A4** extracts pin *geometry* using A1's derived pin datatype (`16`), and this step's contact
  partners tell A4 which conductor a pin on `66/44`/`67/44` would reach.
- **B2/B3** consume the five rules above as the sole basis for same-net merging.
