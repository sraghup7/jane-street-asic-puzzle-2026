## 2. The interface, found in the layout

The 13 documented ports were located by their labels on **70/5**, checked against the positions
Step 1 recorded, and each resolved to exactly one net — and the direction system then confirmed
them independently:

| port | dir | net | instance terminals | output terminals |
|---|---|---|---|---|
| `clk` | in | 1608 | 1 (`clkbuf_16.A`) | 0 |
| `rst_n` | in | 322 | **88** (`RESET_B` 84 + `SET_B` 4) | 0 |
| `enable` | in | 1187 | 2 (`B`, `DIODE`) | 0 |
| `I` | in | 520 | 45 | 0 |
| `O[0..7]` | out | 8 distinct nets | 1 each (`X`) | 1 each |
| `success` | out | 2380 | 5 | 1 (`Q`) |

**Every input port carries zero output terminals and every output port exactly one.** That is a
structural confirmation of the documented interface that does not use a single pin name: it falls
out of the direction inference. `rst_n` reaching 88 flip-flops, and the clock root being a single
`A` pin driven by `clk`, are the shapes a clock-and-reset structure should have.

## 3. Direction derived from structure, not from names

The method is a small linear system, not a name heuristic. One unknown per `(master, pin)` class
— output or input — and one equation per net: **a well-formed net has exactly one driver**, so
the number of its terminals that are outputs must equal 1 (0 for an input-port net). Four
structural rules are propagated to a fixed point:

* **A** — a class with more terminals on one net than the target allows cannot be an output: it
  would put two drivers on that net.
* **B** — once the outputs accounted for meet the target, every unresolved class on that net is
  an input.
* **C** — exactly one terminal unaccounted for, while the target still needs an output: that
  terminal's class is the output. This is what identifies the 21 unused outputs.
* **D** — a cell with signal pins must have an output; a logic cell driving nothing is not a
  cell. So if every pin of a master is decided except one, that one is the output.

Rule D was needed and was found by looking at the data rather than guessing: the residual
ambiguity was four flip-flop outputs (`dfxtp_2.Q`) each sitting on a large net alongside a few
undetermined pins, with the equations unable to pick. Notably rule D *did* fire for the antenna
diode's `DIODE` pin being decided elsewhere while leaving genuinely passive cells alone.

**Nothing is glossed about the residual.** 2 of 286 classes stay undetermined, and the plan
requires exactly this outcome — "any class the system leaves undetermined is reported, not
assumed". Net 766 is `{a31oi_2.Y, o31a_2.A2 (input), o32ai_2.A2}`: `Σx = 1` is satisfied by
either undecided terminal, and both masters already have a pin classed as an output, so no rule
can break the tie. The honest reading is that the *netlist structure admits more than one
consistent direction assignment here*, not that the extraction is wrong — and because net 766 is
therefore excluded from judgement, the integrity claims in §1 are stated over the 738 nets whose
classes are all decided, not over all 741.

## 4. The single-terminal nets, classified

B4 measured 30 and B5 classifies every one, which is the amended acceptance clause:

| class | count | what they are |
|---|---|---|
| `unused_output` | 21 | 15 `clkbuf_4.X`, 5 `conb_1.HI`, 1 `conb_1.LO` — outputs driving nothing |
| `port_out_terminal` | 8 | `O[0..7]`, each driven by an `and3_2.X` |
| `port_in_terminal` | 1 | the clock root's `A`, driven by `clk` |

An unused output is not a floating input, and the direction inference is what makes that
distinction checkable rather than asserted. A by-product worth noting for Phase C: the eight
output-port bits are driven by `and3_2` gates, one per bit.

## 5. A bug in my own checks, caught by the checks failing

The first run of this stage reported three failures — all of them on checks that were *correct
about the data*. The cause: this stage's helper is `check(name, passed, detail)`, but I had
written several new checks in the **gate's** `check(label, actual, expected)` style. So
`check(..., [], [])` became `passed=bool([])=False` (failing on good data) and
`check('13 port nets ...', len(port_rows), 13)` became `passed=bool(13)=True` — a check that
**could never fail**, regardless of how many ports were found.

That is the fifth instance of this project's recurring bug class, and the first one found in a
check written to catch it. All 22 checks were converted to the boolean convention and the failing
set re-verified; the gate now asserts `len(port_rows) == 13` rather than merely being non-zero.

## 6. A process mistake worth recording

I ran `run_all.py` while a `fault_inject.py` run was still in flight, and B3's gate failed with
`2625 distinct cluster ids` for 2626 nets. That is not a defect — it is the fault-injection
harness's own documented hazard: it holds artifacts in a mutated state between restores, so
anything reading them concurrently sees a deliberate fault. The number was literally my
`nets: cluster ids made non-unique` mutation, read mid-row.

The harness behaved exactly as designed (stamp file present, artifacts restored, exit 0, stamp
removed). The lesson is on me: `fault_inject.py` says "run it alone", and that means not running
the suite for the duration, not merely not starting them together.
