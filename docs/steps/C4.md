# Step C4 — symbolic region-map decode (Δ5, the headline differentiator)

**Status: INCOMPLETE.** The **column** counting is resolved and verified (11 column counters, one per
column, each marking exactly that column's two stars; no row counters exist). The **region map is
not** — a candidate star grouping was tested and **refuted** (R7), so the regions' cells remain
unknown and `recon/derived/regions.json` is still not written.

Plan reference: `docs/03_our_plan.md` §C4 / §6.6. Acceptance criteria unchanged and unmet.

## What C4 must produce

The hidden map: a partition of the 121 grid cells into **11 regions**, each with capacity 2 stars,
rendering as an 11×11 picture reading **"JS"**. Δ5 is that we *read the logic* rather than probe the
chip (which is what the published solution did), so the map must come out of the netlist's
structure, not out of crafted stimulus.

## What is established

Recon used `probe_c4a.py` (dump every signal in the design: `$dumpvars(0, dut)`, parsed
scope-aware) and then a chain of analyses. Every claim below is a set-equality or periodicity
result against the 121 positions of attempt 1 (cycles 4..124).

### R1 — The design tracks the column as a **mod-11 counter** ✅

`i0855` (net `n169`) holds its value at positions **10, 21, 32, 43, 54, 65, 76, 87, 98, 109, 120**
— every 11th position, 11 holds in 121. That is bit 0 of `p mod 11` exactly: in a mod-11 count,
consecutive values flip bit 0 except at the 10→0 wrap. So the position is tracked as
**column = p mod 11**, and 121 = 11 × 11 with a wrapping column counter.

### R2 — All 11 columns are decoded ✅

Eleven nets are high on exactly `{p : p mod 11 == k}`, one per k, with the complementary form
`col != k` for the others — found by set equality, no thresholds:

```
col==2 n2185   col==4 n2277   col==5 n2419   col==6 n1391 (and n2418)
col==8 n2533   col==9 n2612/n873   col==10 n1876
col!=0 n1972   col!=1 n2074   col!=3 n2229   col!=7 n2478
col!=9 n1002/n879/n907   col!=10 n1029/n978
```

So the design's vocabulary is `col==k` and its negation, exactly as a decoder would be built.

### R3 — Rows are decoded as **ranges**, not equality ✅

```
n1542           row == 5
n1752, n1797    rows 5..10        (row >= 5)
n1800,n1805,n1842  rows {2,3,4,6,7,8,9,10}   (row >= 2 except row 5)
n233, n235      row >= 9 (high on row 9 from col 9) ...
```

`row >= c` style signals, and the row-5 exclusion above is the first sign of *carved* structure:
rows ≥ 2 **minus row 5**.

### R4 — Region-shaped signals exist, and they carve columns ✅ (the lead)

Grouping every net by its exact change-position set (identical set ⇒ identical function, with no
thresholds) surfaced signals that are **a column minus a few cells** — the shape a region boundary
leaves behind:

```
n2438, n2440   18 changes at [6,7, 17,18, 28,29, 50,51, 61,62, 72,73, 83,84, 94,95, 116,117]
               = column 6 shared by every row EXCEPT rows 3 and 9
n1391, n2418   the same signal WITHOUT the carve-outs = the full column 6
```

The pairs `(6,7), (17,18), …, (116,117)` are the on/off transitions of a one-cell-wide pulse in
each row, so a *missing* pair is a *removed cell*: rows 3 and 9 of column 6 are in some other
region. Two further nets are irregular blobs rather than columns or row ranges
(`n929`/`n974`, `n15`/`n50`), and those are the best current candidates for actual region shapes.

**This is the lead, and it is not yet the map.** What is missing is the *join*: the carve-out
signals identify cells that belong to a different region; not yet assembled into a partition, and
not yet reduced to a closed-form function of (row, column).

### R5 — The decode vocabulary is **column ranges and small cell blocks** ✅

Indexing every net's *cell set* and querying candidate shapes directly (a dict lookup, not a
search, so all 19 000 rectangles are tested rather than sampled) gives the design's full vocabulary:

```
rows 0..10 x cols 2..5   n1307      col ranges, overlapping
rows 0..10 x cols 3..6   n1001      (so they are comparisons, not regions)
rows 0..10 x cols 6..8   n1568
rows 0..10 x cols 7..9   n547
rows 1..2  x col 6       n892       2-cell vertical bar
row 4      x cols 2..10  n195       9-cell horizontal bar
rows 6..8  x cols 8..9   n1323      3x2 block
row 10     x cols 9..10  n2007      2-cell bar
rows 0..0  x cols 0..1   n2055+n2057+n2058+n2119+n2138+n2169+n2172+n2187+n2194+n2235+n2236+n393
```

**No net is a pure diagonal class** (`(c-r) mod 11` or `(c+r) mod 11`), so the map is *not* the
natural 11-class diagonal partition that would give 11 regions of 11 cells for free. What the design
does contain, beyond whole columns and rows, is exactly the pieces a hand-drawn partition is built
from: column *ranges*, and small blocks like `rows 1..2 x col 6`. Those blocks are the best
candidates for region interiors, and they are the thing to assemble.

### R6 — What was ruled out ❌

Four approaches were tried and failed, and are recorded so they are not retried:

* **Per-region 2-bit counters.** C3's carry-chain search found 13 two-bit chains; this step's
  exhaustive re-derivation ("every change is +1 mod 4, reaching 2, in both attempts") yields only
  **7**, and 4 of those are adjacent bit pairs of the *ones-counter*, not separate counters. So the
  "13 region counters" reading is **not sound**, and any map built on it would be built on sand.
* **Those counters being region-gated.** The sharper test: walk each counter's **D-cone** through
  the gate graph (output pins are `X/Y/LO/HI/Q`, so the graph is directed) and look for a net in
  that cone that is high at every one of the counter's marks in *both* attempts. For **6 of the 13
  chains the cone contains no such net at all** — the counter's next-state logic does not reference
  any signal that covers its own increment events, so they are not gated by a region decode. For the
  other 7 the cone yields 7–16 candidates, which is under-determined by 3 marks.
* **A partition of the enables.** If the counters were regions their enables would partition the
  grid, so choosing one candidate per counter is a constraint-satisfaction problem with a decidable
  test. Searched: **no disjoint cover of the 121 cells exists** among the cone candidates. That
  falsifies the region-counter reading independently of the counting argument above.
* **A binary region id.** No group of nets changes only at region boundaries: the change-position
  groups jump from ~30 changes (column and row-range decodes) straight to hundreds.

## Why it stopped here rather than producing a map

A region map produced by guessing which irregular blob is which region would be exactly the
"asserted, not found" failure the plan forbids, and it would propagate into D (the solver runs *on*
the region constraint) and into AC6. The plan's fallback for C4 — *report the bit-level truth table
and decode from that, still symbolically* — is the right next move and is a *smaller* piece of work
than what was attempted here, but it has not been done yet, so C4 is reported as incomplete.

## The concrete next step

The carve-out structure (R4) says the map is built as `col==k` **minus** cell sets. So:

1. Enumerate, for every column k, the nets of the form `col==k AND <row-predicate>` — i.e. take
   `col==k`'s cone and *subtract* every row-range signal in its fanin. The carve-outs are the
   region boundaries inside that column.
2. Take the resulting per-column remnants as the region *cells*, then group remnants that are the
   same region (the map's regions must each have capacity 2, and each cell exactly one region) —
   and check the partition condition, which is decidable.
3. Reduce each region to a closed form over (row, column), evaluate for p = 0..120, render 11×11,
   and compare with "JS".

Step 3 is where the Δ5 claim is cashed: the closed form must be *derived* from the cone.

## R7 — The counting structure is resolved ✅ (added after E1)

E1 made this possible by exercising the success path, and it produced the piece C4 had been missing:
under the winning feed, **22 flops have exactly two in-window transitions, and both transitions fall
on star cells**. Two marks per counter is exactly right — the puzzle's solution has two stars per
region, per row and per column, so every counter counts to two — and the marks can be classified by
whether they share a row or a column:

```
marks share a column  ->  a per-COLUMN counter
marks share a row     ->  a per-row counter
marks share neither   ->  a per-REGION counter (a region is neither a row nor a column)
```

Result of that classifier (`probe_c4n.py`):

```
two in-window marks, both stars, sharing a column : 19 flops over ALL 11 columns
  column  0: i0630, i1044      marks (1,0) (3,0)      <- exactly column 0's stars
  column  1: i0706, i1184      marks (7,1) (10,1)
  column  2: i0285, i1213      marks (3,2) (5,2)
  column  3: i0432, i1250      marks (8,3) (10,3)
  column  4: i1339             marks (4,4) (6,4)
  column  5: i1367             marks (1,5) (9,5)
  column  6: i1391             marks (4,6) (7,6)
  column  7: i0556, i1454      marks (0,7) (2,7)
  column  8: i0433, i1583      marks (5,8) (9,8)
  column  9: i0555, i1553      marks (0,9) (2,9)
  column 10: i0837, i1584      marks (6,10) (8,10)
two in-window marks, both stars, sharing a row    : 0
two in-window marks, both stars, sharing NEITHER  : 3 (plus one false positive, below)
```

**Every column has a counter and each one's marks are exactly that column's two stars** — an
independent match against the winning grid, not against anything we assumed. The three
sharing-neither flops (`i0763`, `i0405`, `i0798`) are the unambiguous **region** counters, and one of
the four candidates (`i0277`) is a false positive: it is a *ones*-counter bit, which C3 had already
identified, and it fires twice by coincidence.

That makes **22 counters = 11 column counters + 11 region counters** — and the arithmetic closes
exactly: 19 column-marked flops + 3 region-marked flops = 22, with 8 of the 11 columns holding *two*
such flops. The ambiguity is real and is resolved by the stars: a region whose two stars happen to
lie in one column produces a counter with the same marks as that column's counter, so those 8 pairs
cannot be separated by marks alone.

**A candidate star grouping, and the test that refuted it.** The 11 two-mark flops pair the 22 stars
into `(1,5)+(6,4)`, `(4,4)+(7,6)`, `(4,6)+(9,5)` (the three sharing-neither pairs) plus eight
within-column pairs, and that partition looks like a grouping into regions. **It is not established,
and the attempt to check it failed in a way that is informative.**

A region's counter enable must be high at that region's two stars and **low at the other twenty** —
a star in another region cannot trigger it. That is 22 known positions, and it can be tested against
every net in the design at once (`probe_c4o.py`, `probe_c4p.py`):

```
region pair            nets high at both marks   of those, also low at the other 20 stars
A (1,5)+(6,4)                     253                          0
B (4,4)+(7,6)                     280                          0
C (4,6)+(9,5)                     268                          0
D (0,7)+(2,7)                     265                          0
G (8,3)+(10,3)                    294                          0
E (1,0)+(3,0)                     260                          1   <- n979
F (3,2)+(5,2)                     267                          1   <- n2185 (the col-2 net)
H (5,8)+(9,8)                     285                          1   <- n2533 (the col-8 net)
I (0,9)+(2,9)                     257                          4   <- n2612/n873 (col 9)
J (6,10)+(8,10)                   286                          1   <- n1876 (the col-10 net)
K (7,1)+(10,1)                    265                          1   <- n1131
```

For the within-column pairs the only net that satisfies the 22-point constraint **is the column net
itself** — so those pairs are consistent with the column counter and say nothing about regions. For
A, B, C, D and G **no net at all** satisfies it: there is no signal in the design that is high at
exactly those two stars. A region whose two stars are that pair would have an enable, so **those
pairs are not regions.** The star-grouping claim is withdrawn.

What survives is stronger than what the grouping was for:

* **11 column counters, one per column, each marking exactly that column's two stars** — verified
  against the grid, 11 of 11.
* **No row counters** (`shares a row` is empty over all 92 flops), so "2 per row" cannot be a
  counter-per-row; the 12-stage shift register is the obvious place to look, since it holds a whole
  row plus one.
* The three sharing-neither flops (`i0763`, `i0405`, `i0798`) are real counters that fire exactly
  twice on star cells, and they are **not** region enables. Their pairs are
  `(1,5)+(6,4)`, `(4,4)+(7,6)`, `(4,6)+(9,5)`, which link the six stars of columns 4, 5 and 6 into
  three cross-column pairs — one per unordered pair of those columns. What they count is an open
  question, recorded as such; what they do **not** do is decode a per-cell region.

## The concrete next step (revised again)

The enable test above is reusable and sharp: any candidate region must be findable as a net high at
its stars and low at the others. That gives two routes:

1. **Ask what the three sharing-neither counters count.** They are exact counters with exact marks,
   so a hypothesis about them is testable the same way. Candidate readings to test: a *pair of
   columns* (columns 4–5, 4–6, 5–6 are exactly the three pairs their marks link), or a counter for
   the two stars' *shared* property. If it is a column-pair counter, the design may be checking
   "2 per column" with a second, coarser set of counters.
2. **Look for the region map where the row check must be.** With no row counters, the row logic is
   combinational, and it sits on the shift register's 12 cells. The region decode is most likely in
   the same logic family, so the 12 shift-register outputs are the natural inputs to reduce over —
   with the carve-out and interval pieces from R4/R6 as the pieces to assemble.

## R8 — The simulation-free evaluator exists and is verified ✅ (added after C5)

Δ5 is not a claim about a *result*, it is a claim about a *method*: the map must be read out of the
logic rather than interrogated with stimuli. That needs an instrument, and the instrument now exists
and is verified. `recon/scratch/symb.py` is the recovered netlist as boolean equations — 630
combinational cells, 92 flops, cell functions taken from `cells.py` (the models C1 and C2 gated) —
evaluated with **Kleene three-valued logic on the gate structure** and clocked in Python. No
iverilog, no vvp, no designed stimulus.

Three-valued matters: B5 found exactly one structurally undriven net (net 806, loaded by
`a311o_2.A1` and `a31oi_2.A1`) and C1 measured it reading `z`. A blanket "unknown in, unknown out"
rule poisons O[1] and O[4]; a controlling value on another input decides the gate (`0 & z = 0`).

### Verification, in both directions

```
vs the reference waveform (the puzzle's own example_inputs.vcd values):
    cycles 312; output mismatches 0; unknown bits 0                    -> exit 0
vs iverilog on OUR netlist (all 734 module-scope nets of c4a.vcd, probe_c4z.py):
    compared (both defined): 225956; disagreements 0
```

### The five defects that had to be found first

Each of these made the equations disagree with the simulator, and each is a fact about the *design
or the tooling*, not a typo:

1. **Icarus reuses one identifier per net, re-declared in every scope.** An `ident -> name` map
   keyed by identifier therefore ends up holding the *deepest* declaration (an instance-pin path).
   Only **734 of 1714** identifiers have a module-scope declaration; that is the set that carries
   the `n<cluster>` wire names. `probe_c4y.py` reported 1 dut-scope net before this was fixed.
2. **The four reset-less flops power up `X`.** `dfxtp_2` has no asynchronous control, so those four
   flops start unknown and stay unknown until their D is first defined. Starting them at 0 sent
   their X into a `SET_B` cone, which is what split the two evaluations at cycle 4.
3. **An `X` asynchronous control means *hold*, not "not asserted".** Treating `X` as 0 latched a
   set/reset that never happened: `n1813` (`i1094`, a `dfstp_2`) read 1 where the flop holds 0.
4. **The reference stimulus changes mid-cycle.** `enable` rises at 40000 ps, *inside* cycle 3
   (edges are at odd multiples of 5000 ps), so the D a flop latches at the edge that *ends* a cycle
   is built from the **next** cycle's inputs. Clocking with the current cycle's inputs lagged the
   entire state by one step. This is why the divergence began exactly at cycle 4.
5. **A VCD prints a vector MSB-first.** The reference's `O` string is big-endian; assembling it
   LSB-first left the first 125 (all-zero) cycles matching and made the first message byte appear
   bit-reversed (`0x2A` for `0x54`).

Defect 1 is a tooling trap; 2 and 3 are properties of this design; 4 and 5 are conventions. All five
are recorded here because each produced *plausible* wrong output rather than an error.

### Status of the map: still not read

The instrument works; the *labelling* is the open problem. With `enable` held high and `I = 0`, the
index counter does **not** advance one position per cycle — `n169` (i0855, which marks
`p mod 11 == 10`) is high with spacing `2,2,2,2,3` — so cycle number cannot be used as the cell
index, and the row-5 anchor `n1542` never fires at all. The only *established* alignment is the
reference's own feed (1 bit per cycle while `enable` is high on cycles 4..124, offset 4 measured in
E1).

The fix is to label slots by the **index state itself** — the 10 `position_counter_bit` flops — and
not by cycle number, then sweep. `probe_c4ad.py` already runs the `I = 0` sweep, the exact-cover
search over net high-sets, and the two-star test; it needs that state-keyed alignment and nothing
else.

## R9 — The symbolic sweep: the map is not a per-cell decode ❌ (added after R8)

R8's verified evaluator is what makes this possible. Method: run the reference's **control timeline**
(`rst_n`/`enable`) with **`I = 0` at every position** — no stars, so nothing star-gated is active and
what moves is only the index decode — and evaluate every net at all 121 positions. The alignment is
re-derived inside the run instead of assumed: the 121 slots give **121 distinct position-counter
states**, and all **11 of 11** column-decode nets come out high exactly on the positions with
`p % 11 == k` (the same 11 nets c4e found, found again here). Nothing is taken on trust.

```
nets with a non-empty high-set over the 121 cells : 424
nets whose high-set is exactly one column         : 9    (cols 2,4,5,6,8,9,10 + two duplicates)
nets whose high-set is exactly one row            : 0
nets whose high-set is exactly 11 cells           : 13
partition of all 121 cells by any set of nets     : NONE
k=4 / k=5 combinations giving an 11 x 11 split    : NONE   (27 decode-shaped nets)
```

Two negatives, both decisive:

* **No one-hot region enable exists.** If the design checked "two stars per region" with a per-cell
  decode there would be a net high on exactly one region's cells. There is none: the only 11-cell
  nets are whole columns and *sliding windows of 11 consecutive positions*.
* **No recombination of decode-shaped nets gives the partition either.** `k` nets produce at most
  `2^k` classes, so 11 classes needs `k >= 4`; `k = 4` and `k = 5` were searched over the 27 nets of
  8..16 cells (17 550 + 80 730 combinations) — zero hits.

What the vocabulary actually is, from the shapes:

```
n821    row 10 cols 0..9  +  (9,10)   = positions 109..119    <- 11 consecutive positions
n233    (8,10) + row 9 cols 0..9      = positions  98..108    <- 11 consecutive positions
n277    (6,10) + row 7 cols 0..9      = positions  76.. 86    <- 11 consecutive positions
n275    same high-set as n277 (two nets, one function)
n1391 n2418 n873 n2612 n2185 n2277 n2419 n2533 n1876   = 9 whole columns
n45 n170 n202 n583 n776 n927 n979 n1131 n1323 ...      = irregular carve-outs (5..23 cells)
```

The index decode is built from **whole columns, sliding 11-position windows, and carve-outs** — not
from 2-D region blobs. This closes C4's original hypothesis by evidence rather than by running out
of time: with R6 (no disjoint cover), the enable test (no net high on exactly a candidate star pair)
and this, "the region map is readable as per-cell selects" is **refuted**.

Two readings survive, and they are the remaining work:

1. **The window reading.** An 11-position window is exactly "one row's worth" of the stream, and the
   design has one per offset. That is the natural structure for a "two per row" check — so the
   hidden constraint may be enforced over **windows of the position stream**, not over 2-D regions,
   which would explain why no per-cell decode exists at all.
2. **The plan's own fallback** (§C4): report the **bit-level truth table** and decode from that,
   still symbolically. That table now exists — this probe emits 424 nets x 121 self-verified
   positions — so the fallback is executable as-is.

C4 stays **incomplete**. What has changed is that the *shape* of the answer is now constrained by
evidence: it is not a per-cell region decode.

## R10 — Star-gated enables: the I=1 sweep, and no second cover ❌ (added after R9)

R9's sweep used `I = 0`, which was wrong in *kind*, not merely in alignment: a region enable is
`star(cell) AND cell in region`, so with no star anywhere no region enable can ever assert. R9 was
only ever looking at index decode. The fix needs no crafted stimulus — the puzzle's own all-ones
input puts a star on every cell at once, and the design's own message for it is `BIG BANG`.

Sweep with `I = 1` on the same control timeline (cycles 4..124 = positions 0..120):

```
nets with a non-empty high-set              : 622   (vs 424 with I = 0)
whole-column nets                           : 13    (11 distinct columns, 2 duplicated)
whole-row nets                              : 1     (n1542 = row 5)
exact cover of the 121 cells                : the ELEVEN COLUMNS
alternative covers, rows/columns excluded   : 0
```

So the covers that exist are the column partition (and by symmetry the row partition) — the two
mechanical constraints already known — and **nothing else**. 38 non-row/column nets of 8..14 cells
appear in the `I = 1` sweep, including the sliding-window nets R9 found; no eleven of them tile the
grid. (The first cover the search returns is the columns, which trivially satisfies "11 classes of
11 cells with 2 stars each" — so a cover existing proves nothing until rows and columns are
excluded.)

### And the map is not affine either

`probe_c4ai.py` tests every affine candidate `region(r, c) = (a*r + b*c) mod 11` over 40 small
`(a, b)` pairs, against the winning grid and against the 40 sampled valid-looking patterns
(regenerated with the same 2-switch walk as `probe_c5b`). **Only `(1,0)` and `(0,1)` satisfy the
winning grid at all**: every diagonal, anti-diagonal and mixed form fails to give 2 stars per class
on the target. So the map is neither row/column nor diagonal in form.

### Where that leaves C4

Three independent negatives now agree: no one-hot per-region decode (R9), no non-trivial exact cover
(R10), no affine map (R10). Whatever enforces the hidden constraint — C5 proved one exists, 40 of 40
— is **not** a partition of the 121 cells that the design decodes combinationally, in any form a
hardware decode would take. That is a finding in its own right, and a different one from the plan's
assumption.

The remaining readings, in cost order:

1. **Streaming.** R9's vocabulary is 11-consecutive-position windows, i.e. the design reasons about
   the *stream*; a "2 per row" check over the last 12 shift-register bits is exactly a windowed
   check. If the hidden constraint is windowed too, then there is no grid decode to find and C4's
   question is answered in the negative: the map is not computed cell-by-cell at all.
2. **Cone support.** For each of the 92 flops, determine symbolically which input *positions* its
   D-cone is sensitive to. That is the strict form of Δ5 ("express the cone, evaluate it") and it is
   what a region counter's enable must look like. It needs a *symbolic* evaluator (support
   propagation) rather than a concrete one — the next real piece of work, not a rerun.

Cost note: the evaluator now orders gates by level (`_order_gates`), which cut a 121-position sweep
from minutes to seconds. The three-valued validation was re-run after that change and still reports
**312 cycles, 0 mismatches, 0 unknown bits**.

## R11 — Per-cell trigger sets: validated instrument, no region counters ❌ (added after R10)

If a flop counts stars arriving in a cell set `S`, then with a single star at cell `x` its D differs
from its Q at position `x` **exactly when `x ∈ S`**. So `{x : D(x) != Q(x)}` *is* that flop's cell
set — its decode, read off the equations. One probe per cell (121 evaluations; seconds each once the
gates are level-ordered), no simulator, and each probe's pattern is one star with the rest of the sky
empty.

The instrument passes its own control. Of 92 flops, 57 have a non-empty cell set, and among them:

```
ones-counter bits (C3)  i0317 i0192 i0623 i0902 : 120 cells  <- counts the star at every cell
position-counter LSB    i0855                   : 109 cells
TEN column counters     i1184 i1213 i1250 i1339 i1367 i1391 i1454 i1583 i1553 i1584
                                                : 11 cells each = one whole column, and the
                                                  stars in each are exactly that column's two
```

Every one of those agrees with something established independently — C3's ones counter, C4's eleven
column counters, C4's mod-11 position counter. The instrument is therefore reading the design
correctly, which is what makes the negative below worth something.

**And no flop's cell set is a region.** There are 54 distinct cell sets; the only 11-cell ones are
the ten columns plus `i0405`, which is irregular (5 rows x 3 cols, containing *no* star of the
winning grid) and is one of R7's three cross-column pair counters. No set of flops partitions the
grid into 11 classes of 11 cells.

Two limitations, stated rather than glossed:

* Only **ten** of the eleven columns appear. Column 10's counter is not detected because its last
  cell is position 120, the final position, where the end-of-sweep checks fire in the same cycle and
  mask the trigger. The other ten are exact.
* A region counter whose enable fires at a cell but whose D coincidentally equals Q there would be
  missed. This is the same sensitivity limit the enable test in R7 has, and it is the reason the
  result is reported as "no region counter is visible" rather than "none exists".

The reading is now: the design counts **per column** (11), **per cross-column pair** (3, R7), and
**in total** (the ones counter) — and it does not count per region per cell. With R9 (no one-hot
enable), R10 (no exact cover, no affine map) that is **four independent instruments, one verdict**:
the hidden constraint is not a per-cell region decode. The two remaining readings are unchanged:
the stream/window reading, and cone-support analysis with a symbolic evaluator.

## R12 — The published method, run on our netlist ❌ (user instruction, 2026-09-13)

Recorded as a **deviation from Δ5**: on the user's instruction this step used the method of the known
solution instead of our own symbolic one.

The published method, verbatim from our step-2 notes (`docs/02_known_solution.md`, Stage 8):

Implemented faithfully: 121 single-star stimuli, one per cell, each evaluated through the R8-verified

**First, a correction to my own earlier check.** I had required every region to be exactly **11

disjoint cover of the 121 cells by 11 of them : NONE

**So the published method, run on our netlist, does not reproduce a region map.** That is the same

defect. Two readings remain, and they are the honest ones for the writeup:

1. **Our step-2 notes compress Stage 8.** "Per-region *saturation* counter" may mean the counter
   reaching 2, and a saturation is only observable when **two** stars fall in one region — so a
   single-star stimulus could never fire one. The faithful experiment is then a *pair* of stars: feed
   `(x, y)` and record which counter saturates. That recovers the region **pairings**, not the
   extents, and it is cheap — the natural next probe.
2. **The map may be an interpretation, not a mechanism.** If the chip never computes a region map,

   structure — which is consistent with everything here, including the published solution never
   decoding their own `magic_index` LUT either.

**Consequence for the acceptance criteria.** Q2(a) requires the "JS" region map *recovered
independently*. A map produced by the published method is not independent in the sense AC6 meant —
Δ5 *was* the differentiator. If such a map goes into the writeup, its provenance must be stated, or
AC6 must be re-scoped. Flagged for the user rather than decided here.

## R13 — The star grouping is CONFIRMED and R7's withdrawal is REVERSED ✅ (2026-09-13)

R7 derived a grouping of the 22 stars into 11 pairs from the *marks* of the two-mark flops, then
withdrew it because the "enable test" found no net high at exactly a candidate pair's two stars and low
at the other twenty. **The withdrawal was wrong, and the test was the flawed half.** The enable test
assumes the region mechanism is a *level* signal — a wire that goes high exactly on a region's cells.
The mechanism is a **counter whose increment tracks the star**: a star is marked by the counter
*changing* there, and a change need not correspond to any single net being high. R7 threw away a correct
result because it was checked with the wrong kind of test.

The test that settles it (`probe_c4aq.py`): take the **accepted** board and remove one star at a time —
22 runs — and for every flop compare its whole state trajectory (cycles 4..124) against the unmodified
run. Every star produces the same ~29-flop global signature (the ones counter, the position counter, the
12-bit shift register) **plus exactly four flops unique to that star**. Those four are two 2-flop
counters: the star's **column** counter, and a second counter shared with **exactly one other star**.

The outcome is a **perfect matching of the 22 stars into 11 pairs**:

```
(0,7)+(2,7)  (0,9)+(2,9)  (1,0)+(3,0)  (3,2)+(5,2)  (5,8)+(9,8)
(6,10)+(8,10)  (7,1)+(10,1)  (8,3)+(10,3)                       <- within a column
(1,5)+(6,4)  (4,4)+(7,6)  (4,6)+(9,5)                           <- cross-column
```

which is **exactly R7's grouping**, including the three cross-column pairs and the fact that they link
columns 4, 5 and 6 as a triangle. R7's derivation was right.

Why R11's single-star probes never saw these counters while this test does: R11 put **one** star on the
board, so "2 per row" fails the moment row 0 ends, and the region counters are evidently only live while
the pattern is still on a valid path. Perturbing the **accepted** board keeps the logic running and the
counters appear immediately. That also explains R12: the published method's single-star stimulation, run
on this design, cannot work — not because the method is wrong, but because its stimulus puts an invalid
board on the wire.

**What is still missing is the extents.** This test narrows it precisely: the eleven region counters are
now *identified flops* — `i0730`/`i0763` for the (1,5)+(6,4) region, `i0378`/`i0405` for (4,4)+(7,6),
`i0764`/`i0798` for (4,6)+(9,5), `i0557`/`i1481` for (0,7)+(2,7), `i0512`/`i1525` for (0,9)+(2,9),

## R15 — The eleven counters are COLUMN counters with a one-column decode lag ✅ (2026-09-13)

The decisive measurement (`probe_c4ax.py`): run 60 random **valid** boards and accumulate, for each of the
eleven counters, the cells that make it tick. One board only ever reveals two ticks per counter (it
saturates), so accumulation is what makes the shape readable.

Every counter's tick set is a **vertical run in exactly one column, one column to the left of the column
its stars live in**:

```
counter            stars in column   tick set concentrated in
C(0,7)+(2,7)              7            column 6   (8 of 12 cells)
C(0,9)+(2,9)              9            column 8   (9 of 10)
C(1,0)+(3,0)              0            column 10  (8 of 16, the wrap)
C(3,2)+(5,2)              2            column 1   (6 of 9)
C(5,8)+(9,8)              8            column 7   (8 of 11)
C(6,10)+(8,10)           10            column 9   (7 of 9)
C(7,1)+(10,1)             1            column 0   (8 of 13)
C(4,4)+(7,6)            4 and 6        columns 3 and 5
C(1,5)+(6,4)            5 and 4        columns 2..5
```

So the eleven counters are **the eleven column counters**, and their enable decode is registered one
column behind the star that feeds them — a one-step pipeline lag.

**This explains every confusing result in C4 at once.** A star in column `c` changes both the column-`c`
counter and the column-`(c-1)` counter, so any test that groups stars by "which flops react to them"
pairs a star with its neighbour column's counter. That is exactly what R7's grouping and R13's
"confirmation" of it recovered — **so those two results are artifacts of the lag, not evidence of a
region structure.** R13's conclusion is hereby corrected: the pairing is real as a *phenomenon*, but its
cause is the decode lag, not regions.

**Where that leaves the question.** There is no per-region counter in this design. The hidden constraint
demonstrably exists (C5: 40 of 40 valid-looking boards rejected) but is **not** implemented as a
per-cell region decode (R9, R10) and **not** as a per-region counter (R11–R15). So the options are now
narrow and evidence-based:

1. the constraint is enforced over the **stream** (the sliding 11-position windows of R9 are the only
   unexplained structure left), in which case "11 regions spelling JS" describes the *shape of the
   answer* rather than machinery the chip contains;
2. or it is enforced by logic that depends on state in a way none of these tests can see.

**C4's honest result:** the region map is **not** recovered, and — now with a reason rather than an
absence — the counters it was expected to be recovered *from* are column counters with a lag. That is a
finding about the published method's premise, not a failure to look hard enough.

## R16 — The stream/window hypothesis is refuted, and the verdict route is closed by uniqueness ❌ (2026-09-13)

Five probes, three refutations, two structural facts worth keeping.

**1. The verdict oracle works at message level.** `probe_c4ay.py` and `probe_c4az.py` decode the
design's output stream: the accepted board reads `(* TWO STARS *)`, and boards carrying every
visible rule read `TRY AGAIN` — not `TWO NOT TOUCH`. This matters because the board generators in
R14/R15 checked adjacency in four directions; the puzzle's rule is **eight** (`tools/target.py`).
Re-checked with the proper rule, the rejection stands: C5's "the hidden constraint exists" is now
established at message level, not merely as "the run did not succeed".

**2. The stream/window hypothesis is refuted.** `blocks.json` shows the input shift register has
twelve taps, delays 0..11 — the design does hold the last twelve cells of the stream — so a
hidden rule over *windows of the stream* was the natural next guess. `probe_c4be.py` tested it:
for every offset h, count the stars in each 11-cell window of the stream. The answer satisfies
"every window holds exactly two stars" only at **h = 0**, which is rows — and every valid board
satisfies that. No shifted window fits. ❌

**3. Uniqueness closes the verdict route entirely.** The published writeup proves the accepted
input is the *only* accepted input (`assume(input != answer)` → UNSAT). So the accepted family has
exactly one member, and **no experiment that reads accept/reject can ever identify the map**: the
partition "rows" already gives two stars per class on every valid board, and with a single positive
example there is nothing behavioural to separate it from the true map. This retires the
stimulus-probing family of methods for us, including the published one: it can *corroborate* a map
already in hand, never derive one.

**4. No per-cell region function exists in the netlist** (≤ 3–4 nets). `probe_c4bb/bc/bd.py`
searched for a net-set whose combined value over the 121 positions partitions the grid into eleven
classes each holding two of the answer's stars and each being violated by *some* rejected board.
The unconstrained criterion is satisfied **only** by row-shaped partitions (a row plus wrap
strays), which are artifacts of the stream counters, not a map; with the shape constrained to
R13's "eight whole columns plus three regions over columns 4, 5, 6", nothing at all. Note the
shape is dead on its own terms anyway: whole-column regions would admit many boards, contradicting
the uniqueness in (3). ❌

**5. The eleven counters are not region counters.** `probe_c4bd.py` records where each counter
pair changes state on the accepted board: **five of the eleven never change at all**, and the rest
change at cells that do not match the labels R13 gave them (e.g. the pair labelled `(0,7)+(2,7)`
changes only at cell `(1,5)`). The flip test cannot distinguish "this counter counts this cell"
from "this counter reacts when this cell arrives", so R13's pairing was a labelling, not an
identification. R15's reading — counters keyed to the stream, off by one — is the better fit. ❌

**6. The answer is isolated under the visible rules.** A 2×2 swap of two stars is the *only* move
that preserves two per row and two per column at once. From the accepted board there are only 189
such swaps, and just **10** leave the board adjacency-free (`probe_c4az.py`).

**Where C4 stands.** The hidden constraint exists and is now confirmed at message level; it is
not a per-cell decode, not a per-region counter, not a window rule, and not recoverable from the
design's verdicts, because there is exactly one accepted input to learn from. The one route not
yet tried is the one that worked for this puzzle's *other* hidden message: the chip's geometry.
The Morse strip (`PER ARENAM AD ASTRA`) was read out of the **GDS**, not the netlist. If the map
is drawn rather than computed — which the "spells JS" description suggests — it is a picture in
the layout, and `tools/render.py` plus `recon/derived/layers.json` are the instruments for it.

exact cover by 11-cell increment sets is the columns and nothing else. So the eleven counters

**Calibration, for the record.** Scoring each candidate offset by the fraction of increment cells

the unreliable pair table, not from the mapping.

**2. `success` is the state of a single flop.** `probe_c4bk.py`: the driver of the `success` net is
`i1594.Q`. The chip's verdict is literally that flop's value at cycle 126.

**3. The verdict's logic is a small cone, and inside it the hidden condition is two flops.**
`i1594.D`'s cone is 104 nets / 57 flops: 27 `column_counter_bit`, 18 `winning_only_bit`, 6
`ones_counter`, 5 `unclassified`, 1 `message_counter`. Boards that satisfy all four visible rules
make the visible state identical, so **any net in that cone that differs between the accepted
board and a rejected one is the hidden check** -- and exactly two flops differ at the decision
cycle (`probe_c4bl.py`):

```
i0455  = 1 on the accepted board, 0 on all 20 rejected boards
i0798  = 0 on the accepted board, 1 on all 20 rejected boards
```

**4. The hidden check is a stream automaton, not a spatial decode.** `probe_c4bm.py` prints the
cones with cell types: `i0455` is a sticky latch, `D = Q + NOT 669` where
`669 = NAND4(I, enable-gated, i0432, i0406)` -- it is *set* when a star arrives while other
condition flops hold, and it then holds. `i0798` is a bit of a star counter whose increment is the
usual `NAND4(I, enable, lower bits)`. Both read the **input bit and enable directly**, with the
position dependence carried by earlier condition flops, i.e. by the 12-tap shift register: the
condition is a **pattern over the stream**, not a lookup on the cell.

**What this means for the project.** The published writeup's Stage 8 -- "stimulate each cell, see
which per-region saturation counter fires" -- describes a mechanism this netlist does not contain:
there are no per-region counters, only eleven column counters and a handful of one-bit condition
latches. That is a finding about the published method's premise, and it is why the map could not
be recovered by re-running that method: the objects it probes do not exist. The hidden rule is a
condition on the incoming stream, held in a small number of latches, and the remaining work is to
**decode `i1594.D` as a function of the stream** -- 104 nets, which is tractable -- rather than to
keep hunting for a map.
