## 1. Why this is the gate that matters

Everything through B6 was verified against **evidence about itself**: each gate re-derives an
artifact from its own inputs. That is strong, and it caught the B5 defect — but it cannot catch an
error shared by a derivation and its own check, and the B5 episode is the proof: the fabrication
passed its own gate for weeks of commits before a *different* step's interface assertion saw it.

`warmup/` is the one place with an **independent answer**: a real small design, its real layout, and
the real netlist that layout was built from. So B7 runs the pipeline on it and compares.

The thing that makes B7 worth something is that it shares the *code*:

| shared with | what |
|---|---|
| B3/B4 | `connect.build_engine` — the **flattened** engine, not B2's separate hierarchical spike |
| B4 | `netlist.probe_placements` — the same prober, on 230 placements instead of 1618 |
| B6 | `emit.render_body` — the same renderer, and `build/cells.v` unchanged |

Those three were factored out of the chip-specific stages *for this step*. Placements are the only
input that differs. A second implementation agreeing with the first would prove nothing; the same
implementation agreeing on a second design proves something. That the factoring changed no
behaviour is itself asserted — B3–B6 regenerate their artifacts byte-identically, and they passed
between the refactor and this run.

## 3. The third comparison, which the plan did not ask for

`02_netlist_with_power_rails.v` is the same netlist with the rails added. Compare it against what
our extraction can see:

| pin | reference | ours | |
|---|---|---|---|
| `VGND` | 230 | **230** | recovered |
| `VPWR` | 230 | **230** | recovered |
| `VNB` | 137 | **137** | recovered |
| `VPB` | 137 | **0** | **not visible in the layout** |

That was worth adding, because A5's predicted gap class was — until now — checked only against our
own reasoning. Here an independent document says the flow *did* connect 137 `VPB` pins, and the GDS
genuinely contains no routeable geometry for them. The class is even named for the pin
(`vpb_well_tie_no_routeable_geometry`). So the omission is a real difference between what a netlist
says and what a layout draws — implant tie versus routed wire — and not a hole in our extraction.

`VNB` is the control that makes that argument rather than asserting it: it is a body pin too, the
reference connects exactly as many of them, and we recover **all** of them.

## 4. Two bugs this step's own gate caught in my B7 code

Both were found by the first run of `check_stepB7.py`, and neither was visible from the stage's own
happy-path output:

1. **Duplicate wire declarations.** I emitted the `wire` lines myself *and* passed `wires` to
   `render_body`, which emits them too. `iverilog` rejected the file with ~90
   `'n4' has already been declared in this scope` errors. The stage had already printed PASS for
   all six of its own checks; only the compile check saw it.
2. **A path leaked into the artifact.** The report recorded `str(OUT_NETLIST.relative_to(ROOT))`,
   so when the gate redirects `OUT_NETLIST` into scratch to regenerate hermetically, the report
   differed from the committed one by that path alone. The artifact depended on where it was
   written. Fixed with a literal constant — the same class of non-determinism B4 hit with a stored
   runtime, and the same fix: **an artifact must be a function of the inputs, nothing else.**

A third failure was the gate's own expectation being wrong: it asserted we assign neither `VPB` nor
`VNB`, and we assign `VNB` (137/137). The claim is now the narrow, true one — the *only* supply pin
we cannot see is `VPB` — with the whole table pinned so it cannot quietly widen.

## 6. Phase B is closed

Every step in it is now verified against something outside itself: A-phase numbers by
`check_recompute.py`, B1–B5 by their gates, B6 by a parse-back round trip, and B7 by an independent
netlist for a design we did not author.

Two facts to carry into Phase C:

1. **`net 806` is the design's one undriven net**, and the warm-up has no such net, so it is a
   property of *this* GDS rather than of the engine. *Answered by C1:* it reads **`z`**, not X — an
   undriven `wire` is high impedance, where `x` is what an unwritten `reg` reads — and forcing it to
   0 and to 1 both leave every interface output identical over the waveform, so it changes nothing
   *there*. The scope stays explicit: E1 re-probes it on the winning vector.
2. **The cell models are still hypotheses.** B7 proves they compile and that their interfaces match
   their masters; it does not prove `a2111oi_2` computes what the model says. *Quantified by C1:*
   negating each model one at a time shows the replay catches **37 of 66** and passes silently on
   **29**. That number is the reason C2 exists, and the list in `recon/derived/c1_power.json` is
   what C2 has to cover.

## 7. Correction found by C2: the emitted supply ports were not ports

`build/warmup.v` as B7 emitted it put the reference's five ports in the header and declared
`inout VGND;` / `inout VPWR;` in the **body**. A body-level `inout` for a name the header omits is
not a port, so the file advertised an interface it did not have: the first caller that connected it
(C2's testbench, §4 of `C2.md`) failed with `error: port ``VGND'' is not a port of dut_ours`. Jane
Street's own `02_netlist_with_power_rails.v` lists `VPWR` and `VGND` in the header, and so does B6's
`build/puzzle.v`; only this file differed.

Fixed in `tools/puzzle/warmup.py` — the emitted ports are the reference's ports in their own order,
then the supply ports we emit, **in the port list** — and the artifact was regenerated. The gate grew
a check for it (39 → **40**), and the check is the interesting part: a caller must be able to connect
every port the netlist is *documented* to have, where "documented" means the reference's ports plus
the supplies the supply table shows we emit. Building that caller from the file's own header would
have compiled happily and agreed with any header at all.

What B7's gate did check, and why it passed: the file compiles cleanly (`iverilog -Wall -t null`),
and its port list matched `01_netlist.v`'s six ports exactly — which is precisely what the defective
header said. **Compiling a file proves it is well formed, not that its interface is real.**
