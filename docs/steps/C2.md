# C2 — Warm-up functional equivalence, exhaustively (and what it can actually see)

**Status: PASS.** Stage `warmup-equiv` PASS; stage `warmup-power` PASS; gate
`tools/checks/check_stepC2.py` → **43/43**; **20/20** gates in the suite.

*Artifacts:* `build/warmup_equiv_tb.v` (the generated harness), `recon/derived/warmup_equiv.json`,
`recon/derived/c2_power.json`.
*Stages:* `python -m tools.puzzle warmup-equiv`, `python -m tools.puzzle warmup-power`.

## 1. The claim, and how it is stronger than C1's

C1's oracle is real but *narrow*: one waveform, 312 cycles, and — as §6 of its record measured — it
can see 37 of the 66 cell models it negated. C2 is a second, structurally different oracle: a design
whose Verilog we hold (`warmup/00_source.v`) and whose layout we extracted (`build/warmup.v`).

The plan asked for "an exhaustive or randomised sweep of `(A, B)` pairs". **C1's measurement settled
that argument, so C2 is exhaustive**: 8 serial bits per operand means every one of the 65536 pairs
fits in a single simulation costing milliseconds of simulated time. Sampling an oracle that can be
exhausted is a choice to accept known coverage loss for no gain.

Result: **`S` agrees between our extracted netlist and Jane Street's RTL on all 65536 pairs.**

```
pairs checked                   : 65536
S high: reference / ours        : 15 / 15
mismatches ours-vs-reference    : 0
mismatches reference-vs-formula : 0
mismatches ours-vs-formula      : 0
C2 WARM-UP EQUIVALENCE: PASS
```

## 2. The comparison is against the RTL, not against a formula

Both designs are instantiated in **one testbench** and driven by **one stimulus**:

| instance | source |
|---|---|
| `dut_ours` | `build/warmup.v` — our netlist, rebuilt from `warmup/04_final.gds` |
| `dut_ref` | `warmup/00_source.v` — the reference, top module renamed (see §3) |

Three assertions come out of that, in increasing order of what they rule out:

1. the **reference** implements `a + b == 496` on every pair — so the protocol we apply is the
   protocol the design implements;
2. **our netlist** matches the reference on every pair — the equivalence claim itself;
3. **our netlist** implements the function on every pair.

Restating `A + B == 496` in Python and comparing against it would have made the source irrelevant,
and would not have noticed if our reading of the protocol — bit order, enabling, when `S` is
sampled — was wrong the same way twice. The formula is checked, but as a third witness.

### Nothing about the protocol is typed in

`read_warmup_source` derives it from the file: the shift width from the register that shifts
(`output reg [7:0]` → 8 bits), the target from the constant the comparator compares against
(`9'd496`), the serial order from the shift expression
(`parallel_out <= {parallel_out[6:0], serial_in}` → the new bit lands at bit 0, so feeding
width bits **MSB first** fills bit 7 first), and the top module from which module instantiates the
shifter. If the upstream file changes, this either follows it or fails loudly.

## 3. The reference is renamed, not rewritten

The emitted netlist is called `adder_demo` because it *is* that design, so one of the two modules
has to move. Renaming the **reference** is the choice that leaves the committed netlist simulated
exactly as emitted, and the rename is asserted to be nothing but a rename: regenerated from upstream
in both the stage and the gate, byte-compared, and required to differ on **exactly one line**, the
module declaration.

The renamed copy lives in `recon/scratch/` and is **never committed** — it is Jane Street's source,
and the same policy that keeps `recon/sources/` out of the tree applies: regenerate it from the
upstream clone rather than redistributing it.

## 4. A real defect in B7's emitter, found the first time anything instantiated the netlist

The first C2 run failed to compile:

```
error: port ``VGND'' is not a port of dut_ours
```

`build/warmup.v` declared its supply ports like this — five of them from the reference, and the
supplies **outside the port list**:

```verilog
module adder_demo (A, B, S, clk, en, rst_n);      // six ports
  ...
  inout VGND;      // not in the list, so not a port at all
  inout VPWR;
```

A body-level `inout` declaration for a name the header omits is **not a port**; Icarus rejects any
caller that connects it. So the file advertised an interface it did not have, and could not be
instantiated the way its sibling can:

| netlist | header port list |
|---|---|
| `warmup/02_netlist_with_power_rails.v` (Jane Street's own rail netlist) | `…, rst_n, VPWR, VGND` ✓ |
| `build/puzzle.v` (our B6) | `…, success, VGND, VPWR` ✓ |
| `build/warmup.v` (our B7) | `(A, B, S, clk, en, rst_n)` ✗ |

Fixed in `tools/puzzle/warmup.py`: the emitted ports are the reference's ports in their own order
**followed by the supply ports we emit**, in the port list. `build/warmup.v` and `warmup_b7.json`
were regenerated; the report now records `interface.ports_emitted` explicitly.

**Two things were worth more than the fix.** First, the reason it survived B7's gate: compiling a
file proves it is well formed, not that its interface is real — `iverilog -Wall -t null` accepts it,
and B7's port-list check compared against `01_netlist.v`'s six ports, which the defective header
matched exactly. Second, the check that would have caught it is now in `check_stepB7.py` (39 → **40**
checks): a caller is generated that connects **every port the netlist is documented to have** — the
reference's ports plus the supplies the supply table shows we emit — and it must compile. The check
uses that documented list rather than the file's own header, or it would agree with whatever the
header says.

Its falsification is recorded rather than assumed: restoring the old header makes **exactly three**
checks fail — the byte-regeneration, the port-list check, and the new one, with C2's own error
message — and regenerating the artifact returns 40/40.

## 5. What C2 can see, measured — and the limit this analysis found

The same question C1's `model-power` asked, asked of this oracle: negate each cell model in a
scratch rebuild of `build/cells.v` and re-run the exhaustive sweep. Only the models the design
instantiates are mutated (16 of the 18 — the rest could not affect it).

```
models mutated                    : 16 of 18 (2 physical-only)
C2 caught                         : 15
C2 silent                         : 1  (clkbuf_16)
C1-blind models instanced here    : 3  (a21bo_2, and2_2, o21bai_2)
  of those caught by C2           : 3
reached by NEITHER oracle         : 26
```

**C2 catches all three models C1 cannot.** That is the second oracle earning its place, measured
rather than asserted. But the same analysis produced the finding that matters more:

> **26 of the 66 cell models are reached by neither behavioural oracle.**

They are the models C1 is blind to *and* the warm-up never instantiates. Neither the chip's waveform
nor the warm-up's exhaustive space can say anything about them, because no stimulus in either design
excites them. For those 26 the evidence stops at B6, whose oracle re-derives each function from the
family name and pin names — which verifies that our Verilog says what we *intended*, not that our
reading of `a21bo` is right.

The union, stated plainly: **C1 catches 37, C2 adds 3, and 40 of 66 models are validated by a
behavioural oracle.** The other 26 are named in `recon/derived/c2_power.json`.

This is not a defect to fix so much as a boundary to know: it is exactly the class of gap the Phase B
review's F1 finding opened, now quantified instead of suspected. **E1 (the winning vector) is where
it can change**: the same measurement can be re-run against the 121-bit stimulus, which will excite
parts of the design this waveform and this warm-up do not.

## 6. Two bugs in my own C2 code

1. **An incomplete format spec.** `INST_TMPL = r'...\(%'` left a stray `%`, so `INST_TMPL % shifter`
   raised `ValueError: incomplete format` before anything ran. A one-character defect that the first
   run caught immediately.
2. **A wrong expectation in my own negative control.** I asserted the altered reference would
   disagree with the formula on the 16 pairs summing to 495. It disagrees on **31** — it now claims
   495 where the function claims 496, so the 15 pairs summing to 496 are wrong too. The run was
   right and my arithmetic was wrong, and the assertion is now exact on both channels rather than
   "non-zero": `(31, 31, 0)`, with `mism_ours_vs_func = 0` being the part that *localises* the fault
   to the reference rather than to our design.
