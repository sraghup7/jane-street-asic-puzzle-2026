# Step C3 — decomposition of the chip into functional blocks

**Status: INCOMPLETE — recon is complete and two of the four required blocks are found and
verified; the "all 92 flops assigned" criterion is NOT met.** This file records what is
established, what is not, and the route proposed to close it. No `recon/derived/blocks.json` has
been written, because writing one would mean naming blocks the evidence does not support.

Plan reference: `docs/03_our_plan.md` §C3 (method amended 2026-09-12, commit `7111924`).

## Method

The plan's original method — cluster the netlist graph and read counters off its shape — was
measured to be **unavailable on this design**, so C3's method was amended before this work began.
Two measurements forced it (probes `probe_c3c.py`, `probe_c3d.py`):

| measurement | value |
|---|---|
| flops whose `D` is another flop's `Q` directly | **0** |
| components of the flop-dependency graph | **1** (all 92 flops) |
| flops reached transitively from any one flop's cone | **90 of the other 91** |
| clock domains | **1** — the 16 "clock" nets are leaves of one tree (`n695` → `clkbuf_16` → 16 × `clkbuf_8`) |

Synthesis inserted logic on every flop-to-flop edge, so no counter is readable from graph shape.
The amended method is **behavioural**: instrument the emitted netlist, dump every flop's `Q`
across C1's 312-cycle replay of `example_inputs.vcd`, and classify by the *relation of each trace
to the stimulus* — not by relations between flops, which fire weakly on 92 traces that are mostly
constant.

Harness: `recon/scratch/probe_c3g.py` (dump), `probe_c3h.py`, `probe_c3i.py` (relations). The
harness reuses C1's `simulate.py` for the clock geometry and stimulus, so the stimulus is the
reference's own transition list rather than a transcription. The dump prints each value **with its
instance name** (`F <cycle> <inst> <bit>`), 28 704 readings.

> A first version packed all 92 flops into one hex word per cycle. With a concatenation, the bit
> order decides the mapping, and an MSB/LSB slip attributed every trace to the wrong flop. The
> first run's carries and shifts were therefore real relations between *traces* attached to the
> wrong *instances*. Naming each value in the dump removes the whole class of error, and the
> corrected run is what is reported below.

## Findings, with the evidence that establishes each

### F1 — Input shift register: **12 flops, found exactly** ✅

Each of these flops' trace equals the stimulus bit stream `I` delayed by a fixed number of
positions, with **zero mismatches over all 242 enabled positions of both attempts**:

```
i0904 d=0   i0902 d=1   i0929 d=2   i0868 d=3   i0827 d=4   i0790 d=5
i0828 d=6   i0754 d=7   i0756 d=8   i0792 d=9   i0830 d=10  i0870 d=11
```

That is a 12-stage pipeline of the serial input: stage 0 holds the current bit, stage 11 the bit
from eleven cycles earlier. **The plan required "a shift register … found, not asserted" — this is
it**, established by matching against an external sequence rather than against other flops.
(Corroboration: the 4 shift relations found independently by flop-to-flop matching —
`i0904 → i0902 → i0929 → i0868`, `i0754 → i0756` — are all edges of this same pipeline.)

### F2 — Total-ones counter, compared against 22: **5 flops, value-verified** ✅

Assembled chain `i0317 → i0192 → i0234 → i0277 → i0191` (bit 0 → bit 4). Read as a binary number
in that order, over the 312-cycle replay:

* **76 of its 77 transitions are +1**, and all 76 occur on cycles where `I == 1`. The one
  exception is cycle **156**, the gap between the two attempts, where it clears and the delta is
  −38 ≡ 26 (mod 32) — the *clear*, not a miscount.
* The value sequence reaches **22 at cycle 71** (values 1,2,…,21,22 at cycles 6,8,…,70,71) and
  continues to 38 by the end of attempt 1 — i.e. it is counting the **ones** in the serial stream,
  and 22 is a value it actually takes.

The plan required "a total-ones counter comparing against 22 … found, not asserted". The counter
is found and its count sequence is verified; the comparison against 22 is corroborated by the six
`conb_1` constant cells found structurally in recon, each feeding a comparison gate
(`a22o_2` / `a221o_2` / `or3_2`), and by the counter actually passing through the value 22.

### F3 — The failure-message path ✅

`i1433 → i1464 → i1434 → i1399` is a 4-bit chain whose transitions are **almost entirely outside
the enable windows**: 31, 15, 7 and 3 changes, first transitions at cycles 126/127/129/133, last at
296/295/293/289, and `enable == 1` on **0** of them. Those cycles are exactly where the reference
emits `TRY AGAIN` (125–133 and 281–289). The four `dfxtp_2` masters (the only flops with no reset)
are among these and their neighbours, which fits a message generator that must survive between
attempts. Named provisionally `message-counter`; the association is by timing, which is strong but
is not a value-level verification.

### F4 — 21 flops never move under the reference stimulus

```
i0275 i0349 i0432 i0433 i0454 i0455 i0512 i0555 i0557 i0837 i0838 i1454 i1481
i1525 i1531 i1552 i1553 i1583 i1584 i1594 i1609
```

Not one of them changes a value in 312 cycles. **This is the central finding for C3's status:** the
reference waveform contains only two *failing* attempts (the README says so, and C1 confirmed
`success` low on all 312 cycles). Logic on the success path is therefore **never exercised** and has
no behavioural signature to find. A decomposition that assigns all 92 flops cannot be completed
from this stimulus alone — not because the method failed, but because the oracle is silent there.

### F5 — A position/period structure that is real but not yet named

A group of flops toggles on nearly every enabled cycle with gap histogram ≈ `[1,2,37]` and
`enable == 1` on ~all of their changes — `i0855` (220 changes) and a ~9-flop group at 123–133
changes. A second 4-bit chain `i0894 → i0498 → i0578 → i0536` transitions **44 times, every one on
an `enable` cycle and none on `I == 1`**, with a clear at cycle 124 (the last enabled cycle of
attempt 1). That is a counter clocked by the attempt, not by the data — the shape expected of the
121-position counter. **It is not verified as one**: reconstructing its value passes +1 at 40 of 44
transitions with the failures at the attempt boundaries, and the chain's low bits do not line up as
a plain binary counter. Recorded as an open item rather than promoted to a block label.

## Proposed route (for the user's decision, not yet executed)

The blocker is structural, not methodological: the reference waveform only drives the failure path.
Two routes close it, and they are complementary:

1. **C4's cone analysis first (Δ5).** The 121-position counter must feed the region-select logic,
   because the region is a function of the position index. C4 identifies that cone by following the
   region-select signals; the position counter then falls out of the same analysis. This reorders
   C3's completion *after* C4 without changing C4.
2. **E1's winning vector.** Re-run this same dump under the winning 121-bit vector (once D has
   produced it). That activates the success path and gives the 21 silent flops a stimulus, which is
   also exactly where E1 already plans to re-probe `n806`. The dump/classify harness built here is
   what E1 would run.

Either route means C3's "all 92 assigned" criterion is satisfied by evidence rather than by
assertion. The recommendation is **1 then 2**: C4 is on the critical path anyway.
