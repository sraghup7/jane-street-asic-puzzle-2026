# Step C3 — decomposition of the chip into functional blocks

**Status: PASS.** All 92 flops are assigned to exactly one block, the gate is 23/23, and two of the
four blocks the plan names are found and verified. The third expectation is **refuted by
measurement** rather than unmet, and that is reported below rather than papered over.

Artifact: `recon/derived/blocks.json` · Stage: `python -m tools.puzzle decompose` · Gate:
`tools/checks/check_stepC3.py`

## Method

The plan's original method — cluster the netlist graph and read counters off its shape — was
measured to be **unavailable on this design** before this step began (method amended 2026-09-12,
commit `7111924`):

| measurement | value |
|---|---|
| flops whose `D` is another flop's `Q` directly | **0** |
| components of the flop-dependency graph | **1** (all 92) |
| flops reached from any one flop's transitive cone | **90 of the other 91** |
| clock domains | **1** (`n695` → `clkbuf_16` → 16 × `clkbuf_8`) |

The amended method is behavioural, and it needs **two stimuli**, which is the part the first attempt
got wrong: the reference waveform contains only failing attempts, so nothing on the success path is
ever exercised and 21 flops never changed value at all — a third of the population had no behaviour
to classify. The second stimulus is the winning vector from `tools/target.py`, clocked in on the
reference's own control timeline (feed offset 4, measured in E1), so the payload is the only
difference between the two runs.

Both harnesses are emitted by the stage (`build/decompose_ref_tb.v`, `build/decompose_win_tb.v`) and
each flop's `Q` is printed **with its instance name**, once per cycle.

> The naming matters. An earlier probe packed all 92 flops into one hex word per cycle; with a
> concatenation the bit order decides the mapping, and an MSB/LSB slip attributed every trace to the
> wrong flop. Printing the name next to the value removes the whole class of error, and the same
> mistake was made twice more in this step's development — a *sorted* block list read the ones
> counter's chain in reverse, turning a peak of 22 into 58. Order is a fact about a counter that
> sorting silently destroys, so `blocks.json` records `flops[0]` as bit 0 upward.

## The blocks

| block | flops | how it was decided |
|---|---|---|
| `input_shift_register` | **12** | each trace equals the serial input delayed by a fixed depth, **0 mismatches over 2 772 position comparisons**, and the *same 12 flops with the same depths* are found under both stimuli |
| `ones_counter` | **6** | seeded from the flop whose changes are a subset of the cycles where `I=1`, then extended by the carry relation; read as a binary number it takes **exactly 22** during the winning feed — the constant the design compares against — with **22 of 23 steps +1** (the exception is the inter-attempt clear) |
| `message_counter` | **5** | every change falls *outside* the enable windows: the only logic that runs between attempts, which is where `TRY AGAIN` is emitted |
| `position_counter_bit` | **10** | changes on ≥ 60 enabled cycles: the fast counting that paces everything else. Contains `i0855`/`n169`, **verified to be bit 0 of `p mod 11`** (it holds at positions 10, 21, 32, …, 120 — every 11th) |
| `region_counter_bit` | **27** | fires **exactly twice** under the winning feed and more under a failing one. Two transitions is what a per-region counter does when its region holds exactly two stars, and every region holds exactly two stars in the winning grid |
| `winning_only_bit` | **18** | fires exactly twice under the winning feed and **never** under the reference: logic the failing vectors never reach |
| `unclassified` | **14** | no signature under either stimulus. Recorded with `changes_reference` / `changes_winning` / `ones_reference` each, never given a function it has not earned |

78 classified + 14 unclassified = 92, and the gate checks the partition both ways: every flop in
exactly one block, and each block's list identical to the assignment.

## Which plan expectations are met

| expectation | verdict |
|---|---|
| **a shift register is *found*** | **met** — 12 stages, depths 0..11, exact against the input under both stimuli |
| **a total-ones counter comparing against 22 is *found*** | **met** — and the counter *takes the value 22* during the winning feed, which is the strongest available evidence that this is the comparison the design makes |
| **an 11-period counter is *found*** | **met** — `i0855` is bit 0 of `p mod 11`: it holds at every 11th position, 11 holds in 121 |
| **a 121-period counter is *found*** | **refuted, not unmet.** The design does **not** count to 121 in one register. It tracks the position as a **mod-11 column counter** (verified) and 121 = 11 × 11 is reached by the column wrapping. The plan's wording assumed a 121-state counter; the measurement says the design does not have one, and forcing the label onto the 10 `position_counter_bit` flops would assert exactly the kind of thing this project refuses to assert. The expectation is recorded as refuted, with the counter that *is* there named instead. |
| **all 92 flops assigned to a named block** | **met** — with the honest caveat that the residual block's name is a *class* (`unclassified`), and 14 flops are in it |

## Why the residual is 14 and not 0

The 14 have no discriminating behaviour: `i0275`, `i0349`, `i1531` never change under either
stimulus; `i0872` and `i0504` change under the reference only; `i0894`/`i0816`/`i0536`/`i0612`/
`i1139`/`i0578`/`i0498`/`i0548` change under both with the same count, so no stimulus separates them;
`i0623` changes 78 times under the reference and 22 under the winning feed. Two stimuli are enough to
classify 78 of 92 flops and not enough for the rest. Classifying them would need a stimulus that
distinguishes them, which is a statement about the stimulus, not about the flops — so they are
reported as a class with their measured signatures attached.

## Evidence

```
./.venv/Scripts/python.exe -m tools.puzzle decompose      # emit both harnesses, classify, write blocks.json
./.venv/Scripts/python.exe tools/checks/check_stepC3.py   # 23/23
./.venv/Scripts/python.exe tools/checks/run_all.py        # 21 gates
```

The gate does not trust the artifact: it re-derives the flop list from `build/puzzle.v`, re-runs the
winning simulation into scratch, re-checks every claimed shift depth against the input, re-reads the
ones counter's value, re-checks that every region bit fires twice, cross-checks the artifact's own
claims (peak, step counts) against the re-derivation, requires each block's list to agree with the
assignment, regenerates both harnesses and requires them **byte-identical**, and floors the compared
sample count so a vacuous run cannot pass.

Fault-injection coverage for this step (6 new mutations: 2 in the harnesses, 4 in `blocks.json`) is
declared in `tools/checks/fault_inject.py`, taking the grid to **84 mutations × 21 gates**; the
focused sweep's verdict is recorded separately when it runs, per the project's practice.
